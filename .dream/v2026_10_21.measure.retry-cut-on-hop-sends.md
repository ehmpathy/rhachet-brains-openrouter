# 🌙 dream: measure, then decide, a retry cut on hop sends

kind: latency · owner: tier-fallback-and-speed-waiver · caught 2026-10-21

## .the cue that fired
5.1 peer `enroll-impl-behavior-intent` i006 nitpick.1 and `enroll-impl-arch-defects` i006 point 3:
each hop pays the openai client's 2 retries first, each up to 60s of `retry-after`. F9 fork 2 was
decided "keep" by robot:director for the 429-hop PR, with no measurement.

## .the gap, precisely
- a throttled host that asks for 30s costs about a minute before the next host is tried
- if a shard's test timeout is shorter than that wait, the hop never lands in time
- no test pins the 60s case: the local stub sends `retry-after-ms: 1`, which overrides `retry-after`
- no number exists for how often a hop send's own retry recovers a transient 429

## .the shape of the fix
1. measure: over live CI asks, count hop sends whose client retry recovered (served on retry 1 or
   2) vs those that hopped anyway; record the wall time each retry cost
2. add 5xx to `asHostFault` first, so a non-last endpoint that drops its retry still hops
3. if the data favors it, send `{ maxRetries: 0 }` per request while a hop remains; the last
   endpoint keeps the client's retries. clamp it with a stub that sends `retry-after: 30` and
   asserts the hop lands without the wait

## .why it is not done in this round
not SAFE without data: the cut trades a transient-429 recovery for speed, and no measurement says
which is worth more. F9 records the call; the rework is clean (one request option per send).
