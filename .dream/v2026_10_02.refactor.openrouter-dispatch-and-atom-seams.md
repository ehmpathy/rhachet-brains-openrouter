## .the gap, precisely

1. `getOneCompletionFromEndpoint.ts`, `getOnePinnedSetCompletion.ts`, and the bare branch of
   `getOneRoutedCompletion.ts` each spread `{ ...request, provider: asProviderPreference(...) }`
   and call `context.openai.chat.completions.create` — three copies of one request shape
2. `genBrainAtom.ts` resolves `supplier.creds` → `new OpenAI(...)` inline; no named communicator
3. `genBrainAtom.ts` calls `genBrainContinuables` twice (tool-call and final-output branches) with
   `response.id ?? null` spelled in each
4. `getOneRoutedCompletion.ts` hand-builds the `route:` report twice (bare and filtered)
5. the composition inside `ask` (the tools guard, the `tools` / `response_format` spreads) has no
   unit test; only the live integration suites reach it

## .the shape of the fix

- `asPinnedChatRequest({ request, filters, only })` — one transformer; the three dispatch sites call it
- `getOneOpenRouterClient({ supplier }, context)` → `{ openai, apiKey }` — one communicator
- `genAtomContinuables({ episode, response, promptText, output })` — one helper, both branches
- one `asRouteReport({ facts, rows })` with `rows: null` for the bare path
- once (2) exists, `genBrainAtom.test.ts` injects a fake `openai` and asserts the request it built:
  tools sent only when not a string ask; `response_format` only for an object schema

## .why it is not done in this round

safe, but not clean: it touches four production files and the atom's main orchestrator after the
stone's guard already passed on them. it ripples into the request each live test sends, so it owes
its own review round rather than a ride-along.
