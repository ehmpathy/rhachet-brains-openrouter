## hazards

### 🔴 H1 — config: `"private": true` flips a public repo to private, and blocks publish

- **what changed**: declapract (`provision-github.bad-practice.implicit-package-privacy`) added `"private": true` to `package.json`. `provision/github.repo/resources.ts` now fails closed: `visibility = pkg.private === false ? 'public' : 'private'`
- **why it breaks**:
  - the repo is PUBLIC today (`gh repo view` → `"visibility":"PUBLIC"`). the next provision run would make it private
  - `npm publish` refuses a package marked `private`, so the next release to npm fails
- **proven by the practice's own readme** (`declapract-typescript-ehmpathy` `provision-github/best-practice/.declapract.readme.md`): *"a repo meant to be public declares `"private": false`, by hand"* and *"`"private": true` also makes `npm publish` refuse. a package published to npm declares `"private": false`"*. the detector flags only a non-boolean (`typeof pkg.private === 'boolean'`), so an explicit `false` satisfies it
- **verify**: `package.json` reads `"private": false`; a re-run of `rhx declapract.upgrade exec` keeps it

### 🔴 H2 — test: `genTempDir()` now requires `{ slug }`

- **what changed**: test-fns 1.10.0 → 1.17.0. `genTempDir` signature is now `(input: { slug: string; ... }) => string`
- **why it breaks**: `src/domain.operations/supply/genZdrRefreshClaim.integration.test.ts:12` calls `genTempDir()` → `TS2554: Expected 1 arguments, but got 0`. the `test-types` ci job fails
- **verify**: `rhx git.repo.test --what types` passes; the integration suite for `genZdrRefreshClaim` passes

### 🔴 H3 — cicd: new `test:lint:cycles` finds cycles in prod dependencies

- **what changed**: the upgrade adds `dpdm` + `test:lint:cycles` to `test:lint`, with `.dpdmrc.yaml` `exclude: []` — node_modules included, by org policy
- **why it breaks**: dpdm walks from `src/**/!(*.test).ts` into dependencies and finds cycles. none sit in `src/`. the cycles were latent on main; the check is new
  - `helpful-errors@1.5.3` (`HelpfulError` ↔ `withHelpfulError`) — via PROD deps `rhachet-artifact@1.0.1`, `iso-price@1.2.0`, and `with-simple-cache@0.17.3` → `simple-in-memory-cache` → `domain-objects@0.31.9`. the repo's own pin, `helpful-errors@1.7.5`, raised no cycle
  - `domain-objects@0.31.7` (`DomainObject` ↔ `hydrateNestedDomainObjects`) and `@aws-sdk/*` STS clients — via `rhachet@1.50.0` → `declastruct-aws@1.5.2`. `rhachet` is a devDep, but prod `src` imports `BrainSpec` from `rhachet/brains` at runtime (pre-extant on main), so this path loads at runtime
  - two entries point into the global pnpm store (`~/.local/share/pnpm/global/...`) — a dep linked from outside the repo; origin unknown
- **constraint**: `rule.forbid.dpdm-exclude-change` — a prod-dep cycle must never be excluded. the repair is to move the prod deps onto cycle-free versions (newer `rhachet-artifact` / `iso-price` / `with-simple-cache`, or a pnpm override onto `helpful-errors@^1.7`), or dispatch upstream
- **verify**: `rhx git.repo.test --what lint` passes with `.dpdmrc.yaml` unchanged

### 🟡 H4 — cicd: secrets now flow through the keyrack firewall

- **what changed**: `.test.yml` drops the explicit `openrouter-api-key` secret input; `publish.yml` passes `secrets: inherit`; each shard runs `rhachet keyrack firewall --env test` over all secrets
- **why it may break**: the firewall forwards only keys `.agent/keyrack.yml` declares under `env.test`, by the secret's exact name
- **name proven**: `env.test: [OPENROUTER_API_KEY]` is declared. test run 42392603677 (pr #25) went green on `suite / test-integration` via the old `secrets.OPENROUTER_API_KEY` map, and those suites throw a `ConstraintError` without the key — so the repo secret carries exactly that name
- **still open**: the firewall step itself runs only in ci
- **verify**: first ci run — integration + acceptance shards reach openrouter

### 🟡 H5 — config: keyrack source moved to jest `globalSetup`

- **what changed**: `jest.{integration,acceptance}.env.ts` no longer call `keyrack.source`; new `jest.*.prepare.ts` call `useKeyrack({ env: 'test' })` once per run
- **holds on read**: `useKeyrack` defaults `lenient` (needed — six extended role keyracks declare keys this repo never reads), goes `strict` only when `declapract.use.yml` declares `awsAccountId` (it does not), and skips in ci. `useWakeOfTestdb` no-ops (no `databaseUserName`); `useWakeOfLivedb` self-gates on a declared tunnel
- **verify**: a local `rhx git.repo.test --what integration --mode apply` sees `OPENROUTER_API_KEY`

### 🟢 ~~H12 — test: acceptance keyrack source is `strict`~~ — disproven

- **the claim**: `jest.acceptance.prepare.ts` sources keyrack `strict` (the old env file used `lenient`), so a local run would halt on an unrelated role's key
- **disproven by measure**: `rhx git.repo.test --what acceptance --against local --env test --mode apply` halted in globalSetup on exactly one key — `ehmpathy.test.OPENROUTER_API_KEY`, which the suites need anyway. no other role's key (e.g. the ghlitch `env.all` `AWS_PROFILE`) was raised. strict moves the same failure earlier; it adds none
- **fact surfaced for stone 3**: this machine holds no `OPENROUTER_API_KEY` under `ehmpath/test` (`keyrack status` lists only an `ahbode` key). integration + acceptance cannot run locally until a human sets it: `rhx keyrack set --owner ehmpath --key OPENROUTER_API_KEY --env test --vault <vault>`
