# vision: api keys via context

## the outcome world

### day-in-the-life with this in place

a developer who builds a multi-tenant application with fireworks ai models can inject credentials per-request via context. two patterns available:

**keyrack shorthand** — auto-discovers `FIREWORKS_API_KEY` from keyrack:
```ts
const context = genContextBrainSupplier<'fireworks', BrainSuppliesFireworks>('fireworks', {
  creds: { keyrack: { owner: 'ehmpath', env: 'prod' } },
});

const result = await atom.ask({ ... }, context);
```

**explicit getter** — custom credential source (vault, kms, db):
```ts
const context = genContextBrainSupplier<'fireworks', BrainSuppliesFireworks>('fireworks', {
  creds: async () => {
    const secret = await vault.get(`tenant/${tenantId}/fireworks`);
    return { FIREWORKS_API_KEY: secret };
  },
});

const result = await atom.ask({ ... }, context);
```

### before/after contrast

| before | after |
|--------|-------|
| `process.env.FIREWORKS_API_KEY` or pre-built `openai` client | keyrack shorthand or explicit getter with env fallback |
| single global api key | per-request credential injection |
| pre-built client passed via context | credential config or getter passed via context |
| no type safety on context | `ContextBrainSupplierFireworks` typed context |
| manual keyrack.get() wrapping | keyrack shorthand auto-discovers key |
| inconsistent with xai brain | consistent pattern, fireworks leads keyrack shorthand |

### the "aha" moment

"oh, i can just pass my keyrack owner and env and it auto-discovers the api key — or i can pass a custom getter for multi-tenant. same pattern as other brain suppliers."

## user experience

### usecases and goals

### two-level credential strategy

| level | pattern | usecase |
|-------|---------|---------|
| **repo level** | keyrack shorthand | org-wide credentials via `{ keyrack: { owner, env } }` |
| **user level** | explicit getter | per-request/per-tenant credentials via `() => Promise<...>` |

### usecases and goals

| usecase | goal | pattern |
|---------|------|---------|
| keyrack auto-discovery | standard credential source, minimal config | keyrack shorthand |
| multi-tenant saas | each tenant uses their own fireworks api key | explicit getter |
| credential rotation | vault returns fresh creds, never stored in memory | explicit getter |
| test mocks | mock creds getter to verify invocation count | explicit getter |
| environment isolation | different creds per env without env vars | keyrack shorthand |

### contract inputs & outputs

**supplies type:**
```ts
type BrainSuppliesFireworks = {
  creds:
    | { keyrack: { owner: string; env: string } }  // auto-discovers FIREWORKS_API_KEY
    | (() => Promise<{ FIREWORKS_API_KEY: string }>);  // explicit getter
};
```

**context type:**
```ts
type ContextBrainSupplierFireworks = ContextBrainSupplier<'fireworks', BrainSuppliesFireworks>;
```

**genBrainAtom signature change:**
```ts
// before
genBrainAtom({ slug }): BrainAtom

// after
genBrainAtom({ slug }): BrainAtom<ContextBrainSupplierFireworks>
```

**ask signature change:**
```ts
// before
ask(input, context?: Empty): Promise<BrainOutput<...>>

// after
ask(input, context?: ContextBrainSupplierFireworks): Promise<BrainOutput<...>>
```

### usage timeline

1. **create context** — `genContextBrainSupplier<'fireworks', BrainSuppliesFireworks>('fireworks', { creds })`
2. **create atom** — `genBrainAtom({ slug: 'fireworks/deepseek/v4-flash' })`
3. **call ask** — `atom.ask({ ... }, context)`
4. **creds getter invoked** — fresh creds fetched per ask
5. **openai client created** — with fresh api key
6. **api call made** — fireworks ai api called

## mental model

### how users describe to a friend

"instead of hardcoding the api key in env vars, i pass a function that fetches it when needed"

### analogies

- **database connection pool** — you don't hardcode connection strings, you get them from config per-request
- **oauth token refresh** — you don't store tokens forever, you refresh them on demand
- **dependency injection** — instead of global singleton, inject per-request

## evaluation

### how well does it solve the goals?

| goal | solved? |
|------|---------|
| multi-tenant credential injection | yes — creds getter per-request |
| consistency with xai | yes — identical pattern |
| backwards compatibility | yes — env var fallback preserved |
| type safety | yes — typed context |

### pros

- **convenience** — keyrack shorthand requires minimal config
- **flexibility** — explicit getter for vault, kms, db, multi-tenant
- **consistency** — same creds pattern as xai (fireworks leads keyrack shorthand)
- **security** — credentials never stored in module scope
- **testability** — mock creds getter, verify invocation count
- **multi-tenancy** — different creds per request via getter

### cons

- **breaking change (minor)** — `context?: Empty` becomes `context?: ContextBrainSupplierFireworks`
  - mitigation: context is optional, env fallback preserved
- **new files** — adds `getSdkFireworksCreds.ts` and test file
  - acceptable: follows established pattern

### edgecases and pit of success

| edgecase | pit of success |
|----------|----------------|
| keyrack key not found | `BadRequestError.throw('FIREWORKS_API_KEY not found in keyrack', { owner, env })` |
| keyrack locked | error from keyrack propagates with unlock hint |
| creds getter returns undefined key | `BadRequestError.throw('creds getter returned undefined FIREWORKS_API_KEY')` |
| creds getter throws | error propagates with original message |
| no context and no env var | `BadRequestError.throw('FIREWORKS_API_KEY required — provide via context or env')` |
| context without creds | falls back to env var (same as xai) |

## what is awkward?

### env var name

xai uses `XAI_API_KEY`, following `{PROVIDER}_API_KEY` convention. fireworks currently uses `FIREWORKS_API_KEY`. this is fine.

### pre-built openai client passthrough

current code allows `context?.openai` as a pre-built openai client. this is different from the creds pattern. options:
1. **remove it** — breaking change, forces migration to creds pattern
2. **keep it** — two ways to inject credentials, inconsistent
3. **deprecate** — keep for now, warn in docs, remove in next major

recommend: **remove it** — the pre-built client pattern is less flexible (credentials cannot be refreshed/rotated) and inconsistent with the creds getter pattern. this behavior is new (v0.1.0) so breaking change is acceptable.

### type naming

- xai: `BrainSuppliesXai`, `ContextBrainSupplierXai`
- fireworks: `BrainSuppliesFireworks`, `ContextBrainSupplierFireworks`

this is fine — follows pattern.
