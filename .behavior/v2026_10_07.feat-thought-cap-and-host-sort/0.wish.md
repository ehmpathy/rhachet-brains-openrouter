## .what

in `ehmpathy/rhachet-brains-openrouter`, accept and forward two openrouter request options the
package sends today neither of:

1. **a thought cap** — openrouter's `reasoning: { max_tokens }` or `reasoning: { effort }`
2. **a host preference** — openrouter's `provider: { sort: 'throughput' }` (and its peers)

## .the outcome

- a caller can set a thought cap per ask, and the package forwards it as openrouter's
  `reasoning` field — by token count, or by effort
- a caller can set a host sort per ask, and the package forwards it as openrouter's
  `provider.sort`
- both are optional; an ask that sets neither behaves exactly as `0.1.3` does today
- when a capped ask spends its whole cap on thought and returns no answer, the reply says so —
  a clear signal the caller can act on, never an empty verdict that reads as success
- each reply reports the thought tokens it spent, so a caller can size its cap from data
- tests prove both fields reach the request body as openrouter expects, and that an unset option
  sends no field at all
- it composes with the latency filter (`beav/feat-latency-filter`) and prompt-cache affinity
  (`beav/feat-prompt-cache-affinity`) trees already in flight: a host sort and an affinity pin must
  not silently fight — say which wins

## .why now

measured in `rhachet-roles-bhrain`: a review ask can think until it runs out of room and return
an empty verdict, and on one measured run the output cost was about 2× the input cost for that
empty verdict. bhrain's `stepReview` wants to pass a thought cap sized to leave room for the reply
and to fit its deadline — "think up to N tokens, then answer" — but `0.1.3` exposes no way to, so
bhrain cannot set it without a workaround around the package.

## .bounds

- the package forwards the caller's choice; it does not pick a cap for bhrain. a tighter cap can
  make a review shallower, so whatever default the tier carries must be generous
