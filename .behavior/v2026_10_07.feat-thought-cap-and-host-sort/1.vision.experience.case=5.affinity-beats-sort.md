# case=5 — filter, pin, and sort meet at one host choice; the order is fixed and named

sharp × critipath. cells: sort ∈ {price, throughput, latency (admitted-set)} × d3 × pin present,
with filter absent [t1]–[t2] (5 cells) and filter present [t3]–[t4] (5 cells).

## .narrative

bhrain's review lanes share a 40k-token prompt prefix. the affinity tree pins the second lane to
host P, which cached it. that lane also asks on a `sort=throughput` slug, and the latency tree
applies its bound by default. three levers, one first host.

the order is fixed (`1.vision.experience.dimensions.md` .precedence):

1. **the latency filter narrows.** a promise, so it binds even the pinned host
2. **the pin takes the first slot**, if P survived the filter. a cache read of 40k tokens beats
   any cold host on cost and prefill (F08)
3. **the sort orders the rest.** if P throttles, the walk falls to the fastest survivor, not the
   cheapest

the sharp edge is a **silent fight**: the caller set `sort: throughput` and P served though Q was
faster, or the caller expected P and got Q. either reads as a defect unless the reply says why.

## .fails safe

- **fast** — no lever is resolved at ask time by trial. the order is computed before the first
  call, and a pinned host the filter excluded is never tried
- **loud** — every reply's supply report names the order it walked. this tree reports
  `supply.choice.sort`, its one order signal. the tree that adds a second lever adds the
  first-host reason: `pin`, or `sort` with the pin's absence or exclusion stated
  (`pin excluded: latency>bound`), so no reply leaves the order to inference (F15)
- **teaches** — the report names which lever won and the rule that made it win, so a caller that
  wanted the sort to lead knows to drop the pin, or loosen the filter, not to file a bug

## .timeline

```
given('[case5] a pin on host P; a slug with sort=throughput; Q is the fastest qualified host; no latency filter')
  when('[t1] P serves')
    then('P is tried first, ahead of Q')
    then('supply.choice names first-host reason = pin, and sort = throughput as the fallback order')   # second-merged tree (F15)
  when('[t2] P throttles')
    then('the walk steps to Q, the fastest of the rest, not the cheapest')
    then('the report names the throttle on P, then Q served by sort')
given('[case5b] the same, plus a latency filter')
  when('[t3] P meets the latency bound')
    then('the order is P, then the rest by throughput, each within the bound')
  when('[t4] P fails the latency bound')
    then('P is never tried; no call is sent to it')
    then('Q serves, as the fastest host within the bound')
    then('supply.choice names first-host reason = sort, and pin excluded: latency>bound')   # second-merged tree (F15)
```

## .the bound

this tree ships `sort` alone, reported as `supply.choice.sort`; that is the only order signal
it emits. it ships no `first-host reason` field: with one lever, the reason has one value and
tells a reader naught `supply.choice.sort` does not (F15). the pin lives in
`beav/feat-prompt-cache-affinity`, the filter in `beav/feat-latency-filter`. whichever tree merges
second wires its lever into the order above and adds the reason field with its values. the
precedence is fixed here so neither tree invents it, and [t1]–[t4] are the clamps the
second-merged tree must make pass.
