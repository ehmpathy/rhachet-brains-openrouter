# case=7 — admitted set, three different faults, then a serve (the densest walk)

feel: happy · care: critipath · actor: caller on a busy day · boundaries: 5

## narrative
a reviewer lane fires one ask on a busy afternoon, from a slug four hosts qualify for: A, B, C,
D. it waits longer than usual — up to a minute per throttled host, while the client retries by
the host's `retry-after` — then the review lands — as if no host had faltered.
before the fix, that same afternoon, the first host's 429 ended the ask and the lane broke.

later, an on-call who wonders why that ask ran slow reads `attempts` and sees the whole walk, in
order: A throttled, B refused, C failed, D served. no log dive.

under the caller's one ask, five boundaries stack — this is why the case gets the deepest
scrutiny:

1. openrouter routes to A; A throttles (429, retry-after 7) → A leaves `only` (throttle boundary)
2. the re-send lands on B; B is unreachable (404) → B leaves, and the model's cached endpoint
   list drops so the next ask reads it live (refusal + cache seam)
3. the re-send lands on C; C answers a host 400 → C leaves (host-400 boundary)
4. the fourth send admits D alone; D serves
5. the served-provider check reads D against the FINAL admitted set `[D]`, not the first
   `[A, B, C, D]` (served-check seam) — and the report carries the trail (report seam)

three status codes, three hops, one shared seam (`asHostFault`), one reply. the trail tells the
whole story in order. this is where the shrink of `only`, the cache drop, and the admitted set
handed to the served check can each go wrong — so it gets the deepest scrutiny.
